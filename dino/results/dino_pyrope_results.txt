# Interpretation — Pyrope's critical path is:
#   pipeB_id_ex.reg_instruction (flop Q)
#     -> DualIssueForwardingUnit combo (~1.7 ns)
#     -> ALUControl.prp:8 nor4 gate with heavy fan-out (~4.27 ns single-cell delay)
#     -> PipelinedDualIssueCPU.prp:272,308 mux selecting ALU input operand
#     -> pipeB_alu (ALU.prp:26) — the 64-bit ripple-carry ADDER (maj3_1 chain,
#        ~85+ maj3 cells × ~0.20-0.26 ns each)
#     -> pipeB_ex_mem endpoint flop (StageReg_6.prp:6)
#
# The Pyrope critical path is a DIFFERENT ripple-carry adder from the Chisel one:
#   Chisel:  PC adder in DualIssueNextPC (~100 maj3, ~24 ns spent in the adder)
#   Pyrope:  ALU  adder in ALU.prp:26   (~85+ maj3, ~19 ns spent in the adder)
# In Pyrope the PC adder is presumably faster (or the forwarding-to-ALU path just
# happens to be slower), so the ALU adder is what's on the critical path here.
# Both flows still use pass.abc.adder=rca so it's the same underlying rca structure;
# what differs is which adder each design's control flow drives longest.

# ---------- Notes on the source that was synthesized ----------
# One line in ./dino_prp/DualIssueIssueUnit.prp:16 was rewritten in-place:
#     BEFORE: _oddPC_T__w1 = io_pc - ((io_pc / 8) * 8)   # arithmetic form of pc%8
#     AFTER:  _oddPC_T__w1 = io_pc & 7                    # semantically identical bit-AND
# Reason: abc leaves the `/8` as a native `div` blackbox (`div_7420`) which opentimer refuses
# to time. The bit-AND version tech-maps cleanly. The Chisel run applied the *same* rewrite
# (`io_pc % 64'h8` -> `{61'h0, io_pc[2:0]}`) to its auto-generated DualIssueIssueUnit.sv, so
# both sides of the comparison saw the equivalent const-mod optimization performed.
#
# Nothing else in dino_prp/ was modified.
